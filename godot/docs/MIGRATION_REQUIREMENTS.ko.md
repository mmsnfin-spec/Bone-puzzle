# BONE PUZZLE 3D — Godot Engine 전환 및 최적화 통합 개발 지시서

## 0. 개발자 역할 및 최종 목표

당신은 Godot Engine, GDScript, 3D 게임 최적화, 게임 UI/UX, 3D 물리 시뮬레이션, 해부학 교육용 콘텐츠 개발 경험이 있는 시니어 게임 개발자다.

기존 GitHub 프로젝트 BONE PUZZLE 3D를 분석하여 Godot Engine 기반의 Windows PC 설치형 게임으로 마이그레이션하라.

**GitHub 원본 저장소**

https://github.com/mmsnfin-spec/Bone-puzzle

**목표 환경**

- Game Engine: Godot 4.7.2 Stable
- Scripting: GDScript
- Platform: Windows 10/11, x86-64
- Rendering: PC 환경에 적합한 Godot 3D 렌더러
- Game Type: 3D Anatomical Assembly Puzzle
- Development: AI-assisted, maintainable architecture
- Output: Godot 편집 가능 프로젝트 + Windows 실행 가능 게임

이 프로젝트는 웹사이트가 아니라 독립 실행형 PC 게임이다.

React, Three.js, Rapier, Vercel 등의 웹 기술을 신규 게임의 런타임 의존성으로 유지하지 않는다.

기존 코드는 기능과 알고리즘을 분석하기 위한 참고 자료로 사용한다.

목표는 기존 게임을 시각적·기능적으로 계승하면서 개발 확장성, 렌더링 성능, 안정성, 코드 유지보수성을 개선하는 것이다.

분석 보고서만 작성하지 말고, 실제 게임 프로젝트와 기능 구현까지 진행하라.

## 2. 게임 방향 및 범위

### 핵심 콘셉트

플레이어가 실제 인체의 뼈를 하나씩 선택하고, 올바른 위치와 방향으로 조립하여 신체 부위별 골격을 완성하는 3D 해부학 퍼즐 게임.

### 1차 개발 목표

- 완전하게 플레이 가능한 HAND 스테이지
- 향후 다른 신체 부위를 추가할 수 있는 스테이지 구조
- 자연스러운 3D 조작
- 정확한 뼈 조립 판정
- 해부학 명칭 학습
- 진행 상태 저장
- 저사양 PC를 고려한 성능 최적화
- Windows 실행 파일 생성

### 향후 개발 범위

- FOOT
- UPPER LIMB
- LOWER LIMB
- PELVIS
- SPINE
- THORAX
- SKULL
- 추후 추가 신체 부위

현재 데이터가 준비되지 않은 스테이지를 임의의 가짜 모델로 구현하지 않는다.

미구현 스테이지는 Coming Soon으로 표시하거나 개발 문서에서 별도 관리한다.

스토리 모드, 해골 부활, 귀가 엔딩, 대규모 게임화 시스템은 이번 개발 범위에서 제외한다.

그러나 향후 해당 기능을 독립적으로 추가할 수 있는 확장 구조는 고려한다.

# 3. 디자인 수정 요구사항

## 3.1 메인 타이틀 완전 간소화

기존 `TitleScreen.tsx`의 복잡한 타이틀 UI를 제거한다.

### 변경 후 타이틀 구성

**화면 중앙**

BONE PUZZLE

**화면 하단 중앙**

아무 key나 눌러 시작하시오

### 반드시 적용할 사항

1. 메인 타이틀 화면에서 `BONE PUZZLE`을 제외한 기존 모든 제목, 부제목, 설명문을 삭제한다.
2. 기존 B/P 로고 텍스트와 타이틀 헤더를 삭제한다.
3. 타이틀 화면의 About, Credits, 난이도 선택, Stage Selector, Start 버튼, 안내 문구 등을 제거한다.
4. 기존의 `3D` 첨자도 제거하고 `BONE PUZZLE`만 표시한다.
5. 배경은 순수한 검은색 또는 기존 디자인과 어울리는 매우 어두운 검은색을 사용한다.
6. 타이틀 화면에는 불필요한 3D 모델과 장식 요소를 렌더링하지 않는다.
7. 제목은 화면 중심에 크고 명확한 세리프 계열 타이포그래피로 표시한다.
8. 하단 문구는 수평 중앙 정렬하고 작은 아이보리색 글씨로 표시한다.
9. 하단 문구에는 부드러운 페이드 또는 깜빡임 효과를 선택적으로 적용한다.
10. 과도한 애니메이션, 글로우, 파티클은 사용하지 않는다.

### 사용자 입력 처리

- 타이틀 화면에서 사용자가 키보드의 일반 키를 누르면 다음 화면으로 이동한다.
- 키 입력은 한 번만 처리하여 중복 화면 전환을 방지한다.
- 키를 길게 누르고 있을 때 여러 번 실행되지 않도록 한다.
- 마우스 클릭으로도 진행할 수 있도록 보조 입력을 지원한다.
- 다음 화면은 별도의 `Stage Select / Main Menu`로 구성한다.
- 난이도 선택, 이어하기, 설정, Credits는 타이틀이 아닌 후속 메뉴에서 제공한다.
- 플레이 도중에는 Escape 키로 일시정지 메뉴를 열 수 있도록 한다.

메인 타이틀은 최대한 미니멀한 디자인으로 제작한다.

기존 Splash Screen과 타이틀은 별개의 화면으로 취급한다. Splash에서 실제 브랜드 원본 이미지가 존재하는 경우 기존 요구사항을 유지하되, 없는 에셋을 임의로 제작하지 않는다.

## 3.2 손 조립 가이드라인 ON/OFF

현재 React 코드의 `Ghost` 컴포넌트는 정답 위치에 반투명 손뼈 모델을 표시한다.

이를 Godot에서 독립적인 Guide System으로 구현한다.

### 요구 기능

게임 플레이 중 다음 두 상태를 자유롭게 전환할 수 있어야 한다.

**GUIDE ON**
- 현재와 같이 정답 위치에 반투명 손뼈 골격을 표시한다.
- 뼈를 놓아야 하는 위치와 형태를 확인할 수 있다.

**GUIDE OFF**
- 반투명 손뼈 골격을 완전히 숨긴다.
- 정답 위치를 나타내는 별도의 윤곽선도 표시하지 않는다.
- 이미 조립한 실제 뼈는 그대로 유지한다.
- 뼈 위치 판정과 정답 데이터는 계속 정상 작동한다.

### UI 요구사항

- 게임 플레이 화면에 `GUIDE ON / OFF` 토글 배치
- 클릭 즉시 변경
- 단축키 `G` 지원
- 기존 Ghost 투명도 조절 기능 유지
- GUIDE OFF인 경우 투명도 컨트롤을 비활성화하거나 숨긴다.
- 토글 상태는 저장 데이터에 포함
- 스테이지 재입장 및 게임 재실행 시 마지막 설정 복원
- 기본값은 ON
- Easy / Normal / Hard와 별개로 가이드를 변경할 수 있도록 한다.

### 렌더링 최적화

GUIDE OFF 상태에서는 단순히 opacity를 0으로 만드는 데 그치지 말고, 불필요한 Ghost 렌더링이 실제로 발생하지 않도록 한다.

가이드 객체는 정답 판정이나 드래그 입력을 방해하지 않아야 한다.

모든 가이드 모델은 실제 뼈와 동일한 위치 및 방향 데이터를 참조하도록 한다.

# 4. Godot 게임 시스템 설계

기존 React 게임 기능을 Godot 구조에 맞게 재설계한다.

필수 기능은 다음과 같다.

### 4.1 Bone Selection

- 개별 뼈 클릭 및 선택
- 선택된 뼈 강조 표시
- 여러 뼈가 겹쳐 있어도 선택 가능
- 작은 뼈를 위한 Piece Index 제공
- 선택된 뼈의 ID 및 학습 정보 표시

### 4.2 Bone Manipulation

- 마우스 드래그로 3D 공간에서 이동
- X / Y / Z축 회전
- 마우스 휠 확대·축소
- 카메라 궤도 회전
- 카메라 Pan
- 뼈 드래그 중 카메라 조작 잠금
- 화면 좌표와 3D 좌표 사이의 정확한 변환
- 키보드 정밀 조작 유지

카메라 방향이 바뀌더라도 드래그 위치가 틀어지거나 물체가 갑자기 튀지 않도록 한다.

### 4.3 Snap System

기존 `SnapSystem.ts` 알고리즘을 분석하여 GDScript로 정확하게 이식한다.

- 목표 위치와의 거리 검사
- Quaternion을 이용한 회전 오차 검사
- 난이도별 허용 범위
- 잘못된 위치에 놓으면 실패
- 정확한 위치에 놓으면 부드러운 스냅
- 배치 완료한 뼈는 고정
- 스냅 판정에 GUIDE 표시 상태가 영향을 주지 않도록 한다.

기존 구현의 기본 규칙을 유지한다.

- Easy: 위치 중심 검사 및 회전 자동 보정
- Normal: 위치 + 회전 검사
- Hard: 더 엄격한 위치 + 회전 검사

기존 위치 허용 오차와 각도 허용 오차를 실제 소스 기준으로 이식하고 단위 테스트로 검증한다.

### 4.4 Bone Name Learning

- 영어 해부학 명칭 입력
- 정답 확인
- 오답 메모 저장
- 공식 명칭 및 등록된 별칭만 인정
- 대소문자 및 앞뒤 공백 처리
- 조립 진행률과 명칭 학습 진행률 분리
- 이름 확인 여부 저장

### 4.5 Hint System

- 스테이지당 최대 5개의 서로 다른 뼈에 힌트 사용
- 같은 뼈의 힌트를 다시 봐도 횟수 차감 없음
- 힌트를 확인했다고 자동으로 정답 처리하지 않음
- Restart 시 힌트 상태 초기화

### 4.6 Intro / Completion

기존 HAND 스테이지의 다음 연출을 기능적으로 유지한다.

완성된 손뼈 → 물리 낙하 → HAND 연출 → 조립 시작

단, 새로운 성능 최적화 구조를 적용한다.

조립 완료 시에는 결과 화면을 표시한다.

- 조립 완료 수
- 총 소요 시간
- 사용한 힌트
- 확인한 해부학 명칭
- Replay
- Stage Select 이동
- 완성된 손 모델 관찰

# 5. 해부학 데이터 보존과 검증

현재 `hand.json`과 기존 GLB 모델을 원본 데이터로 활용한다.

### 필수 보존 데이터

- 27개 고유 Bone ID
- FMA ID
- 영어 및 한국어 뼈 명칭
- Accepted aliases
- 뼈 분류
- 3D 모델 경로
- 초기 위치
- 목표 위치
- 목표 회전
- 스케일
- Snap distance
- 원본 좌표 및 변환 정보
- SHA-256 등 원본 검증 정보

### 해부학 정확성

- Carpals 8개
- Metacarpals 5개
- Phalanges 14개
- 총 27개 오른손 뼈

개별 뼈의 형상을 임의로 재생성하지 않는다.

원본 메시의 해부학적 정확도와 상대적인 크기를 유지한다.

GLB를 Godot으로 가져오는 과정에서 축 방향, 원점, 회전, 스케일의 차이가 발생할 수 있으므로 좌표 변환 검증 코드를 작성한다.

Godot에서 뼈를 모두 정답 위치로 조립했을 때 해부학적으로 연속된 손 골격이 형성되어야 한다.

기존 Three.js 기반 결과와 비교하여 배치 위치와 손 모양의 정합성을 확인한다.

### 데이터 사용 및 라이선스

BodyParts3D 원본과 파생 자료에 적용되는 CC BY-SA 2.1 Japan 라이선스 및 출처 표기를 유지한다.

라이선스 파일, 출처, 원본 고지문을 Windows 배포물에도 포함한다.

타이틀에서 Credits를 삭제하더라도 후속 메뉴의 About / Credits에서 라이선스 정보를 확인할 수 있도록 한다.

# 6. 최우선 요구사항 — 성능 최적화

기존 웹게임에서 JavaScript 및 물리 엔진 실행 비용이 과도하게 측정되었다.

Godot 이전 과정에서는 이 문제를 그대로 재현하지 않도록 구조적으로 개선한다.

## 6.1 Physics Optimization

- Intro의 물리 낙하 단계에서만 동적 물리 연산을 수행한다.
- 조립 단계에서는 뼈를 상시 RigidBody 시뮬레이션하지 않는다.
- 조립용 물체는 직접적인 Transform 제어를 우선한다.
- 필요한 충돌 판정과 클릭 선택은 간단한 충돌체를 사용한다.
- 복잡한 고해상도 메시를 물리 충돌체로 남용하지 않는다.
- 움직이지 않는 뼈는 불필요한 물리 연산을 수행하지 않는다.
- 수면 상태와 충돌 레이어를 적절히 관리한다.
- 물리 낙하 종료 후에는 시뮬레이션을 정지하거나 불필요한 객체를 제거한다.

물리적인 자연스러움과 기존 연출을 유지하면서 CPU 사용량을 낮춘다.

## 6.2 Rendering Optimization

- 화면에 표시되지 않는 모델의 렌더링 최소화
- 불필요한 그림자 계산 제거
- 조명 개수 및 Shadow Map 해상도 검토
- GPU 부담이 큰 투명 재질 사용 최소화
- 공통 재질 재사용
- 불필요한 Draw Call 감소
- 필요할 때만 화면 갱신
- 모델 및 텍스처 자원 재사용
- 과도한 후처리 효과 사용 금지

뼈 표면의 형태와 입체감을 잘 볼 수 있는 조명은 유지한다.

기본 배경은 BLACK, 뼈는 Ivory / Bone White 계열로 유지한다.

## 6.3 Frame Update Optimization

- 모든 뼈가 매 프레임 불필요한 연산을 수행하지 않도록 한다.
- 입력 이벤트 기반 처리 우선
- Transform이 변하지 않으면 갱신 생략
- 반복 객체 생성 및 불필요한 메모리 할당 방지
- 신호 기반 UI 갱신
- 게임 진행 상태와 렌더링 상태 분리
- UI 변경이 전체 3D 씬의 재초기화를 유발하지 않도록 한다.

## 6.4 Asset Optimization

- 기존 GLB 모델을 재사용한다.
- 모델 로딩 및 캐싱 전략을 구현한다.
- 초기 화면에서 전체 스테이지 리소스를 무조건 로딩하지 않는다.
- 필요 시 선택한 스테이지의 에셋을 로드한다.
- 중복 메시 및 재질 생성 방지
- 모델 단순화는 별도의 시각적·해부학적 검증을 통과한 경우에만 수행한다.

## 6.5 성능 측정

Godot Profiler와 Monitors를 활용하여 실제 성능을 측정한다.

확인 항목:

- 평균 FPS
- 최소 FPS 및 프레임 타임 급증
- CPU Frame Time
- GPU Frame Time
- Physics Time
- Draw Calls
- 메모리 사용량
- 씬 로딩 시간
- 타이틀 → 스테이지 이동 시간
- 27개 뼈 조작 시 반응성

최적화 전후를 동일한 PC 사양에서 비교한다.

개발 목표는 일반적인 PC에서 1080p 60FPS를 안정적으로 제공하는 것이다. 단, 최소 시스템 사양은 실제 테스트 후 결정한다.

품질을 무조건 낮추기보다는 불필요한 계산과 메모리 사용을 줄이는 최적화를 우선한다.

### 구조 설계 원칙

1. Puzzle Core는 특정 신체 부위에 종속되지 않도록 한다.
2. 스테이지는 데이터 중심으로 로딩한다.
3. 새로운 신체 부위를 추가할 때 핵심 퍼즐 로직을 다시 작성하지 않도록 한다.
4. Guide System은 독립 모듈로 구성한다.
5. Save System은 독립적으로 관리한다.
6. Physics Intro와 Puzzle Gameplay를 분리한다.
7. UI와 3D 게임 로직을 분리한다.
8. 향후 애니메이션, 업적, 스토리를 추가할 수 있게 한다.
9. 외부 플러그인에 대한 의존은 최소화한다.

# 9. 저장 및 게임 진행 구조

Godot의 `user://` 경로를 사용하는 로컬 저장 시스템을 구현한다.

### 저장 항목

- 스테이지 ID
- 난이도
- 개별 뼈의 위치와 회전
- 배치 완료 여부
- 입력한 뼈 명칭
- 명칭 확인 여부
- 힌트 사용 상태
- 소요 시간
- GUIDE ON/OFF
- 가이드 투명도
- 모션 감소 설정
- 전체 스테이지 진행 상태

저장 파일 손상에 대한 예외 처리를 구현한다.
